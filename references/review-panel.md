# 審查小組協定

最高原則：**以完整找出問題為優先**，不以盡快通過為目標。

## 一、合規檢查（先於科學審查，不交給評審）

合規屬客觀檢查，由程式加清單完成。

**能執行 Python 時：**
```
python scripts/compliance_check.py <計畫書.docx> --config proposal-config.md [--refs refs.ris]
```
程式會檢查：
- 實際頁數（docx 轉 PDF 後計算）與各章節的頁數估算
- 必填章節標題是否齊全
- 參考文獻是否每筆都有 DOI 或 PMID
- 正文是否殘留【待查證】【需補文獻】標記
- 正文 author-date 引用與參考文獻清單是否雙向對應（盡力比對，結果需人工確認）

**人工合規清單（無法執行程式時逐項核對；程式檢查後也要補做程式做不到的項目）：**
- [ ] 年期、語言、經費上限符合 config 硬限制
- [ ] 每一條使用者自訂要求都已落實（逐條列出對應段落）
- [ ] 多年期：方法、預期成果、時程都已分年撰寫
- [ ] profile 列出的特殊必填內容（例如性別分析、資料安全監測計畫、與院內研究人員合作說明）
- [ ] 倫理相關段落與 config 中的研究類型一致

硬限制不符的項目，先修正再進入科學審查。

## 二、審查小組組成

| 角色 | 審查面向 | 必答問題（至少回答） |
|---|---|---|
| ① 領域專家 | 重要性、創新性、研究缺口是否真實 | 缺口是否有文獻支持？是否已有人做過（請實際搜尋）？創新是實質還是包裝？ |
| ② 研究方法學 | 設計是否回答得了問題、偏差、效度、對照 | 設計能否支持因果或關聯宣稱？主要偏差來源與控制方式？干擾因子？ |
| ③ 生物統計 | 樣本數、分析計畫、缺失值、多重比較 | 樣本數能否依所列參數重算出來？每個假說都有對應的分析嗎？缺失資料策略？ |
| ④ 可行性與資源 | 收案率、時程、團隊、場域、經費 | 收案數在時程內做得到嗎（有無前導資料或場域數據）？各年的里程碑能否驗收？團隊專長是否涵蓋所有方法？ |
| ⑤ 倫理與法規 | IRB、知情同意、個資、資料安全、性別分析 | 風險與保護措施？易受傷害族群？資料去識別與保存？是否需要並已規劃性別統計分析？ |
| ⑥ 反方評審 | 假設此案一定被拒 | 最可能的三個拒絕理由，各附計畫書中的證據位置 |
| 主席 | 不提新意見 | 彙整、去重、分級、判定是否通過 |

**依研究類型縮減：** 例如次級資料庫研究沒有受試者招募，⑤ 縮減為資料使用授權、個資與資料安全；純基礎實驗則以動物實驗或生物安全取代受試者相關檢查。縮減情形記入 config。

**對應官方審查面向：** 主席依 profile 的「官方審查面向」把各評審意見歸類對應。profile 沒有官方面向時，使用 NIH 簡化審查架構作為通用參考，並在報告中標明「非該單位官方標準」：
- 研究重要性（重要性＋創新性）
- 嚴謹性與可行性（研究方法）
- 專長與資源（主持人＋研究環境），只判斷是否足夠

來源：https://www.grants.nih.gov/policy-and-compliance/policy-topics/peer-review/simplifying-review/framework （2025-01-25 起適用；最後查證 2026-10-12）

## 三、審查規則

1. **獨立性：**
   - 支援子代理的環境（如 Claude Code 的 Agent 工具）：每位評審是一個獨立子代理，只給計畫書全文、`proposal-config.md`、該角色的說明，不給撰寫過程的對話。六位評審平行執行，彼此看不到意見。
   - 不支援子代理的環境：依序扮演各評審，每位評審開始前明確宣告角色，只依計畫書全文與 config 判斷，不引用撰寫過程中的討論或使用者的解釋。
2. **先找問題，再評分。** 每位評審每個負責面向至少列出一項具體弱點；若認為沒有弱點，必須說明檢查了什麼、為何沒有問題。
3. **每條意見須包含：** 位置（章節／段落）、問題描述、嚴重度（重大／次要）、建議修改方向、依據（文獻、官方規定或方法學原則）。
4. **評分：** 每位評審對負責面向給 1–5 分（5 最佳），附評分理由。
5. **評審可以搜尋文獻**以查證研究缺口或方法學主張，但同樣受零捏造規則約束。

## 四、主席彙整

主席產出：
1. 去重後的意見總表，分「重大」與「次要」，各標註提出者。
2. 各官方審查面向的分數彙整。
3. 通過判定：

**通過條件（全部滿足）：**
- 合規檢查全數通過
- 沒有未解決的重大問題
- 所有面向分數 ≥ 3
- 自訂要求逐條達成

通過時聲明：「✅ 第 N 輪審查通過。」並列出仍可改進的次要意見，由使用者決定是否處理。

## 五、輪數與終止

- 每輪換一組新評審，不給前一輪的對話脈絡，但給上一輪的修改對照表，讓評審確認問題是否真的解決。
- 只要仍有重大問題未解決就繼續下一輪。
- 安全上限 5 輪。到第 5 輪仍未通過時停止，列出未解決項目、原因與建議，由使用者決定繼續修改或定稿。
- 使用者可隨時要求停止或增加輪數。

## 六、修改對照表格式

| 編號 | 評審 | 意見摘要 | 嚴重度 | 回應與修改方式 | 修改位置 | 狀態 |
|---|---|---|---|---|---|---|

狀態：已修改／部分修改（說明）／不修改（附理由，需使用者同意）
